# 운영·백업·업데이트

## 영구 데이터

| 데이터 | 기본 위치 |
| --- | --- |
| SQLite | `data/sqlite.db` / Docker `/app/data/sqlite.db` |
| 로그인 자격 증명·세션 비밀 | `data/auth` |
| 업로드·생성 이미지 | `data/uploads` |
| 암호화 키 | `data/.encryption-key` |
| 창작 지식 | `knowledge/writing` 또는 외부 마운트 |
| 웹 참고처 | `knowledge/web-research/sources.json` 또는 외부 파일 |

Docker에서는 `/app/data` 전체를 영구 볼륨으로 유지합니다. 인증 디렉터리나 암호화 키를 잃으면 기존 로그인 또는 저장된 API 키를 복구하지 못할 수 있습니다.

## 백업

1. 장기 AI·이미지 작업이 없는지 확인합니다.
2. 가능하면 컨테이너를 잠시 중지합니다.
3. `/app/data` 전체를 같은 시점의 한 묶음으로 백업합니다.
4. 외부 창작 지식과 검색 출처 파일도 함께 보관합니다.
5. 복원 테스트에서 로그인, 프로젝트, 업로드 이미지와 `/api/health`를 확인합니다.

SQLite DB 파일만 복사하고 WAL 파일이나 인증·암호화 키를 빼먹지 않도록 전체 데이터 디렉터리 단위 백업을 권장합니다.

## 컨테이너 업데이트

1. 새 이미지를 별도 태그로 빌드합니다.
2. `/api/health`와 AI 대기열을 확인합니다.
3. 기존 컨테이너의 환경 변수와 볼륨 구성을 보존합니다.
4. 기존 컨테이너를 중지하고 이름을 바꿔 짧게 rollback 가능 상태로 둡니다.
5. 새 컨테이너에 같은 `/app/data` 볼륨을 연결합니다.
6. health, 로그인, DB 마이그레이션과 주요 화면을 확인합니다.

## 상태 확인

`GET /api/health`는 서버·DB와 AI 대기열 요약을 반환합니다. 상단 **운영 진단**에서는 외부 서비스 연결과 서버 지표를 확인합니다. health 응답에 비밀·원고 본문이 포함되어서는 안 됩니다.

## 개인정보와 저장소

- `.env`, `.env.*`, SQLite, 인증 파일, 업로드, 모델 파일은 Git에서 제외
- `.env.example`에는 빈 값과 예시 주소만 기록
- 실제 LAN IP, 사용자 홈 경로, 호스트명과 API 키를 문서·테스트에 넣지 않음
- 스크린샷은 계정명·브라우저 정보·원고 내용과 메타데이터를 확인한 뒤 추가
- 공개된 비밀은 파일 삭제 커밋만으로 사라지지 않으므로 즉시 폐기·재발급하고 필요하면 Git 이력도 정리

## HTTP 운영

내부망 HTTP는 전송 암호화를 제공하지 않습니다. 인터넷이나 신뢰할 수 없는 Wi-Fi에서 사용할 경우 TLS 리버스 프록시를 사용하고, 프록시가 전달 헤더를 덮어쓰는 신뢰된 구성에서만 `AUTH_TRUST_PROXY=1`을 설정합니다.
